## Reading these pages

- **Names.** The package is imported as `import jetscape as js`; the bound C++ classes are in `jetscape.pyjetscape_core` (`from jetscape import pyjetscape_core as core`). `import jetscape` also re-exports the most used names at the top level (`js.JetScape`, `js.HadronArray`, ...).
- **What needs a build.** Running events needs the compiled extension (container, Mac wheel or a source build). Reading files needs only the [analysis environment](https://jhputschke.github.io/js-contrib/install/analysis-env/index.md).
- **The Pythonic layer on the C++ classes.** `import jetscape` adds methods and properties to the bound classes (`final_parton_array()`, `hadron_array()`, ...). They are listed on the [C++ bindings](https://jhputschke.github.io/js-contrib/python/api/core/index.md) page under the class they belong to.
- **Build flags.** The stubs follow the build they were made from. Names behind a build option (ROOT, the iColored colour functions, iSS primaries) are listed only when that build had them.
- **No docstring.** A C++ method without one is listed with its signature only; its C++ namesake in X-SCAPE behaves the same.

The guides explain the ideas behind these calls: [The Pythonic interface](https://jhputschke.github.io/js-contrib/python/pythonic/index.md), [Writing modules in Python](https://jhputschke.github.io/js-contrib/python/modules/index.md), [What a production writes](https://jhputschke.github.io/js-contrib/analysis/files/index.md) and [Hadrons](https://jhputschke.github.io/js-contrib/analysis/hadrons/index.md).
